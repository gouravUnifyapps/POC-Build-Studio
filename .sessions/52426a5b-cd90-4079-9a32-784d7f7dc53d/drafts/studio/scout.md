## 3. Boundaries (the ten that bite this build, with the nearest thing the platform can do)
Source for all: NEBULA `skills/nebula-change/references/task-kinds.md` § What each builder can do and its list of work no tool does, unless another file is named.

2. **No tool clones a code app.** `copy_pages`/`copy_entities` are page tools for no-code apps. Nearest: the download-copy-rebind route in § 2.
3. **A task body never carries file contents or a patch.** Nearest: the body points at the source checkout path and says what each screen does.

6. **No secret in any task, spec or reply.** The routine token and Slack signing secret are saved by the main session with `save_env_variables` (`sensitive: true`) and read by name (`ENV.<NAME>`). A builder that needs a secret not given reports a `Security:` line.

9. **An automation has exactly one trigger, and only a `callableApi`/webhook trigger can back an API.** A schedule or app event cannot. Nearest: "Run now" and the weekly schedule are two automations sharing a callable sub-flow; the cloud run's report-back is a `callableApi` automation exposed through API Group, API, client and access profile (key shown once, written to a private file, never read by the Scout or the builders).

## 4. Platform answers (each `Source: NEBULA <skill, sheet id or read>`)

**Q1. Can an automation be triggered by a Slack event (bot mentioned, new message in a channel, bot added)? Trigger operations? Needs a Slack app / events URL? Poll instead?**
Answer: The Slack connector has exactly two triggers: `slack_on_new_message` ("Triggers when a new message is posted in a channel in Slack") and `slack_on_button_click`. The first needs the person to paste the automation's webhook URL into the Slack app ("Setup this webhook url in you Slack App to receive notifications for events"; learn-more link to the Slack docs). Its output carries `event.type`, `event.subtype`, `event.user`, `event.text`, `event.channel`, `event.channel_type`, `event.ts`, `event.thread_ts`, `event.bot_id`, `event.bot_profile.name`, `event.files[]`, `team_id`, `event_id`, `authorizations[].user_id/is_bot`, and a `triggerInputCondition` filter. There is no named "app mention" or "member joined" operation. Consequences (inferred from the output shape, **Check this** with a deployed test): a tag of the bot arrives as a message whose `event.text` contains `<@botUserId>`; "bot added to a channel" arrives as a message event with `subtype channel_join` and `event.user` equal to the bot's user id. Polling works without Slack-side registration: schedule trigger plus `slack_list_conversation_history` (input `token_type` bot_token|user_token, `channel` for a bot token, `oldest`, `latest`, `inclusive`, `limit` 1 to 999, `cursor`, `include_all_metadata`; output `messages[]` with `user`, `text`, `ts`, `thread_ts`, `files[]`, `reply_count`, and `response_metadata.next_cursor`), the bot must be a member of the channel; sender profile via `slack_get_user_info_by_id` (`user.profile.display_name`, `real_name`, `image_24/32/48/72/192/512/original`, `email`); permalink via `slack_chat_get_permalink`; thread via `slack_list_conversations_replies`; file via `slack_get_file_details`/`slack_download_file`.
Source: NEBULA `search_operations slack` (38 operations) + `get_operation_schema slack_on_new_message`, `slack_list_conversation_history`, `slack_get_user_info_by_id`.

3. **Retries and double answers.** Make `bot_thread_ts` NEVER cleared (the open question is "manager_slack_id empty"), and have A1 stop at once when a row's `bot_thread_ts` equals the event's `thread_ts` or `ts` and the reply was already posted; handle only `member_joined_channel` for joins (not the `channel_join` message subtype); filter bot-authored events and other `api_app_id` values in `triggerInputCondition`. The row-exists check alone would make a Slack retry answer "already exists".
4. **One routine fire, not two.** Put the fire in A4 only and have A6 call A4 with `mode build` through `callables_call_automation`; A4's "already running" guard applies to mode plan only. The sensitive token then sits in one HTTP node instead of two (Nebula: a secret in a node is in the run). No ninth automation is needed.
5. **DM path.** In A6 and A5, DM by `slack_open_conversation` then post to the returned channel id (one extra node), with the Stand-in's thread-reply fallback; do not rely on a user id as `channel` until one labelled DM proves it.

Make the first `DEMO-TEST` tag in #pentland-poc the rehearsal row itself ("Pentland PLM Use Case"), and test A5 only through `call_api` on that row.
7. **Env names.** `get_env_variables` and `list_env_variables` are not in the Scout's tool set, so the three names are not proven free; the `env-variable` or main-session step reads them first (a name found must be reused as it is).
8. **`sequential` form and the 60 s poll.** Use the form the compiler accepts (Q9); if a run can outlast 60 seconds with several channels, `sequential: true` queues it, which is the intended behaviour.
9. **Update semantics.** The app's `UPDATE` source is `update_record_by_id` with `upsert false` and a whole-record payload (source-ui §6, data-plan: "an update replaces the whole record"); every automation write to an existing row uses `update_record_fields_by_id` (SET per field) so a field the writer does not know is never blanked.
10. **Possible `file_link` fallback and the documents fetch weight.** FETCH has no projection key, so each list page of `psl_document` carries every `content`; with 6 seeded documents that is fine, and the Documents tab needs no more than the rows of one use case (`triggerInputCondition` on `poc`).
