# POC Studio Live

## Requested outcome
A POC owner tags the Slack bot "POC Studio Agent" in a prospect channel with a use case name; the bot asks who the manager is when the message did not say, and a row appears in the POC Studio Live app, the clone of the POC Studio UI, linked to that one channel. The app follows the channel (History shows who said what, with their Slack picture and time, per use case), starts the cloud Claude Code build from a Build button, shows the PRD and built assets for review, and lets the manager approve a gate, which tells the owner in Slack and continues the build. The journey (Understand, Plan, Build, Deliver), its gates and its iteration counters read from new `psl_` objects, not from the source's Orbit objects. This plan builds the core flow; the skill-improvement loop (feedback aggregated into prompt suggestions an admin approves) is the next change.

## Business rules
- One use case belongs to exactly one Slack channel; one channel can hold several use cases of the same client; a use case name is unique across the app.
- The bot asks "Who is the manager? Tag them here." only when the first message tags no one, and never asks anything else.
- A gate passes only when both the owner (approves in Slack) and the manager (approves in the app) have approved it; the manager is recognised by the signed-in tenant email or full name matching the row, and the Approve gate automation checks it again.
- Documents of a gate are stored `in_review` when the run reports them and shown in the phase's list only after the gate passes ("artifacts logged at approval time"); while the gate waits, the manager reads them in the approval card's "To review" list.
- The PRD is stored as type `brd` and the mockups as type `design`, both HTML, never as type `requirements`.
- A message is logged in History once (the key holds the Slack channel id and timestamp); History belongs to the use case the message names.
- Approving never fails because Slack or the cloud run is down: the approval is saved first, the Slack message and the second cloud run are best effort and add a warning.
- A row with an empty `build_run_id` never starts a cloud run, so approving a seeded row starts nothing.
- No secret is written to a record, a log, a message or a document; the routine token and the report-back key live only in environment variables and the routine.
- Slack is only the messaging channel: conversation and feedback happen in the Claude session, which reports back through the API.
