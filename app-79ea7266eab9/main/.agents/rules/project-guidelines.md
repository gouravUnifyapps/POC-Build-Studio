Project Layout
- Import app code through the `@/` alias (= `app/src/`); avoid deep relative paths.
- Pages go in `src/routes/` (PascalCase file, default export, `function` declaration — match `Login.tsx`). Shared components go in `src/components/` with named exports. Data hooks live in `src/data/`; utilities and stores in `src/lib/`. Directory names are lowercase-dashed.
- `src/main.tsx` and `vite.config.ts` are engine-owned — never edit them. Keep the `APPLICATION_ID`/basename block in `App.tsx` intact when editing routes. Engine-supplied env (e.g. `VITE_APPLICATION_ID`) is injected at build time — read via `import.meta.env.VITE_*`; your own env vars go in a normal `app/.env`, and a key defined there overrides the engine's value.
- Platform env vars with `-` or `.` in the name arrive as `UA_ALIAS_` + that name with those chars as `_` (`theme-env` → `UA_ALIAS_theme_env`; `printenv UA_ENV_ALIASES` is the map). In `.env` / `.npmrc` use the alias — `${theme-env}` silently becomes the literal `env`. Browser: `VITE_THEME_ID=${UA_ALIAS_theme_env}` then `import.meta.env.VITE_THEME_ID`.
- Private npm registries: auth goes in `app/.npmrc` as `//<registry-host>/:_authToken=${TOKEN_ENV_NAME}` — env var name only, never a literal token (platform env resolves it at install and build time). Use the aliased name here too.

TypeScript
- Functional, declarative code; no classes. Use the `function` keyword for components and pure helpers.
- Type props inline or with `type` aliases; interfaces are fine for object shapes — just be consistent.
- Never use `enum` — the build rejects it (`erasableSyntaxOnly`); use `as const` objects and union types.

State and Data
- Dynamic data comes through hooks: `useData` from `@/lib/data`, or the app's data hooks in `@/data`. Never call fetch/axios in a component and never fetch inside `useEffect`.
- `useData`'s `data` is already the unpacked records array (`undefined` while loading/on error). Never re-unwrap it — `extractRecords`/`extractPage`/`extractRecord` from `@/data/bindings` take the RAW `useExecuteWorkflowNode*` envelope, and running one over a `useData` result throws `no response.objects` at run time.
- Shared client state: a zustand store in `src/lib/store.ts` — UI state (dialogs, filters, selection) only, not server data.
- Derive, don't sync: compute values from props/state during render; `useMemo` only when genuinely expensive; never mirror props into state.
- `useEffect` is for external systems (DOM, subscriptions, timers) — not for data flow you can express in render or event handlers.
- Navigate with react-router `<Link>`/`useNavigate` using route paths; never hardcode absolute URLs (the preview is served under a subpath).
- Highlight the nav item for the DEEPEST route path matching `useLocation().pathname`, not every one that matches. `NavLink` marks an item active on routes nested under it as well, so a sidebar listing both `/incidents` and `/incidents/new` lights BOTH rows once you open the child route. Putting `end` on every item instead leaves a detail route like `/incidents/:id` with nothing lit — pick the longest match.

Users and Access
- A brief naming more than one kind of person (agent/requester, manager/rep, staff/customer, admin/everyone else) is an access-control brief even when it never says "role" or "permission". Invoke the `roles-and-permissions` skill during PLANNING, before the data model — access control retrofitted after the UI exists comes out fake.
- Never build a persona switcher: no `PRESET_PERSONAS` array, no `currentPersona.role === '...'` gating, no in-app control that changes who the viewer is. It is a demo of access control that proves nothing. Create one REAL login per persona (`create_app_user`, roles attached) and gate the UI on `useRecordAccess` / `useCanAccessRecord` from `@unifyapps/app-builder-sdk/hooks/permissions`. Build a switcher only if it was explicitly asked for.
- Hand back every credential you create — name, role, username/email and password, verbatim, in a table at the end of your reply. The password is returned once and is unrecoverable afterwards, so a login you do not report is a locked account.

UI and Styling
- Tailwind + the shadcn components in `app/src/components/ui` for all UI; merge conditional classes with `cn()` from `@/lib/utils`. You may restyle the ui primitives, but keep their exported APIs stable.
- No inline styles and no raw hex/rgb: colors only via theme tokens from `src/index.css` (`bg-background`, `text-muted-foreground`, `var(--chart-1..5)` for recharts). Dark mode is the `.dark` class.
- Charts are recharts, never raw divs or SVG. Five rules, all mandatory — this is where generated charts look broken: **long category labels → HORIZONTAL bars** (`layout="vertical"`, category on the YAxis, truncate labels, height ~44px/row), never a vertical bar chart for long labels; **the value axis always includes 0** (`domain={[Math.min(0,…), Math.max(0,…)]}`), or bar lengths lie; **value labels only when ≤ ~8 bars** — a dense or grouped series uses the axis + tooltip, never a number on every bar; **name the quantity once in the card title and keep ticks compact** (`1.2k`), never a unit word on every tick and never a rotated axis title; **every chart in a `<Card>`** with `var(--chart-1..5)` colours. The `design-system-default` skill's Charts section has a complete chart to copy. Reuse a chart kind across pages → extract ONE wrapper into `src/components`, not a folder of duplicates.
- A field you build yourself takes the same inks as the ui primitives: `placeholder:text-placeholder` for its placeholder, `disabled:text-disabled-foreground` for its disabled text, and `disabled:placeholder:text-disabled-placeholder` for the hint an EMPTY disabled field shows — `::placeholder` has its own colour, so without that last one a disabled empty field looks enabled. Never `text-muted-foreground` for any of them: those three follow the app's theme, and `muted-foreground` is secondary text that reads too loud for a placeholder.
- Icons: lucide-react. Toasts: sonner (`<Toaster>` already mounted, with a close X on every toast — restyle it freely, but never drop `closeButton`, or a toast that overstays can only be cleared by reloading). Dates: date-fns.
- A toast that reports an OUTCOME takes the typed call — `toast.success()`, `toast.error()`, `toast.warning()`, `toast.info()` — never bare `toast()`. That is the only thing that colours it: the mounted Toaster paints each state from the app's status tokens (`--success-subtle`, `--destructive-subtle`, …), and a bare `toast()` is the neutral state, so "Saved" and "Couldn't save" come out as the same card. Keep `toast()` for a genuinely neutral note. Same rule off-screen: a status badge, an alert, a validation message and a health dot take `bg-success-subtle` / `text-destructive-subtle-foreground` and friends, never `bg-green-500`.
- A success toast after an automation or a data write says only what came back — its `message`, or a count or id it returned. Never a count from the brief or the plan, and never a toast for a call that was not made: an action the app cannot run gets no button.

Strings
- **Translation is opt-in, and the user decides it.** `src/i18n/languages.json` carries the answer: one language means this app is NOT translated; more than one means it is. There is no in-between and no "wrap it just in case" — pick the state that file names and write every string that way.
- **English-only (the default): write the string where it renders.** Plain JSX text, plain `placeholder`/`aria-label`/`title`/`alt`, plain `toast()` messages, plain labels in module-scope constants. Do not import `useTranslation`, `Trans`, `vocab` or `defineKeys`; do not touch `src/i18n/`; do not run `bun run i18n`, `i18n:lint`, `i18n:types`, `i18n:sync`, `i18n:status` or `i18n:plurals`. The three auth routes, `src/components/copilot.tsx`, `src/lib/passwordPolicy.ts` and `src/data/seed.ts` are the worked examples — they ship this way.
- **Two things still apply in an English-only app, because they are about LOCALE, not language.** Dates, numbers, currency, units and sorting go through `useFormatters()` from `@/lib/i18n` — never a hardcoded `'en-US'`, never by hand; the currency code comes from the record. And a closed set's labels (statuses, kinds, priorities) are declared ONCE beside the set as a `Record<Token, string>` — `STATUSES` in `src/data/seed.ts` — never spelled out at a render site, because a label written at three call sites drifts at two of them.
- **`I18nProvider` stays mounted in `App.tsx` either way.** It is not translation machinery: it owns `<html lang>`/`<html dir>` (what makes Tailwind's `ltr:`/`rtl:` variants work), Radix's direction context, and the locale `useFormatters()` reads. Never remove it.
- **Translated apps — everything below applies only when `languages.json` holds more than one language.** Every user-facing string reaches the screen through `useTranslation` from `@/lib/i18n` (react-i18next), with the English written at the call site as the second argument: `const { t } = useTranslation('orders')`, then `t('title', 'Orders')`. You never create or edit the JSON under `app/src/i18n/` — `i18next-cli extract` writes it from those defaults. `app/README.md` "Strings" is the full contract.
- One catalogue per page, named after the page file: `Orders.tsx` → `useTranslation('orders')` → `i18n/<lang>/orders.json`. A second catalogue in the same file is the same hook renamed: `const { t: common } = useTranslation('common')`. Strings used on more than one page go in `common.json`. Keys are flat and name the ROLE (`emptyState`), not the text (`noOrdersYet`), so the key survives a copy change — to reword, edit the default at the call site and re-run `bun run i18n -- --sync-primary`. That flag is load-bearing: without it extraction adds new keys but never overwrites an existing value, so the old English stays in the catalogue, wins at runtime, and your change never reaches the screen.
- It is not only JSX text: `placeholder`, `aria-label`, `title`, `alt`, `label` and every `toast()` message go through `t()` too. Plurals need their per-form defaults — `t('count', { count: n, defaultValue_one: '{{count}} order', defaultValue_other: '{{count}} orders' })` — because one default copied into every form ships "1 orders". `Intl.PluralRules` picks the form, never `count === 1`.
- Code outside React returns a KEY and its variables, never a sentence; the screen translates it. `@/lib/passwordPolicy` is the file this applies to — English-only it holds a plain `label`, and the conversion gives it `labelKey` + `labelVars`. In constant data, name every key with `vocab()` from `@/lib/i18n`, which makes the key a TYPE and a call site extraction can see; keys named only indirectly with no `vocab()` anywhere must be listed in `preservePatterns` in `app/i18next.config.mjs`.
- Never split one sentence across several `t()` calls to fit markup around it — word order differs between languages and the pieces cannot be reordered. When a sentence needs markup inside it, use `<Trans>` with numbered `components`, which keeps the sentence whole and lets a translator move the elements; the `MissingAgentId` block in `copilot.tsx` is the sentence this applies to. After changing a `<Trans>` default run `bun run i18n -- --sync-primary`, since plain extraction never overwrites an existing value.
- Content data is NOT translated — seeded or fetched alike. The test is WHERE the string arrives from at render time, never what it says: a column header is frontend-authored, a table cell's value flowed in through the data layer. Free-form user input has no correct translation; leave it, and say so.
- Adding a language: add it to `app/src/i18n/languages.json` (`label` + `dir`, read by the runtime) AND to `locales` in `app/i18next.config.mjs` (read by the tooling), run `bun run i18n:sync` to scaffold every key, then translate the values. Empty values fall back to the default language, so a half-translated app stays readable. For an RTL language use logical utilities (`ps-`/`pe-`, `ms-`/`me-`, `start-`/`end-`, `text-start`/`text-end`) throughout instead of `pl-`/`pr-`/`left-`/`right-`.
- Turning translation ON in an app that was built English-only starts with the RETROFIT, not with `i18n:sync`: wrap the existing strings (the app's own screens and the template surfaces it inherited) in `t()` first, convert the label maps to `vocab()` and the out-of-React strings to keys, then extract, then add the language. `sync` scaffolds only what it can see, so a half-wrapped app gets a language that covers a tenth of it and reports itself complete. Load the `localization` skill — it drives this.
- Extra plural forms are handled by `allPluralForms` in `i18next.config.mjs`: Arabic needs six where English has two, and the flag scaffolds them so `i18n:status` reports them as ordinary untranslated keys. `bun run i18n:plurals` is the backstop for the one case that cannot reach — a plural key named only indirectly (`t(rule.labelKey)`), which extraction never regenerates. The engine runs it as a BUILD GATE the moment `languages.json` holds more than one language.
- `bun run i18n:types` regenerates `src/i18n/resources.d.ts` after you add or remove keys — that is what makes a bare `t('typo')` a build error. `bun run i18n:lint` finds strings that never reached a `t()` call and `bun run i18n:status` reports per-language completeness. Run all three from `./app` before you call a TRANSLATED app done. Prefer the `bun run` scripts over the binary — they carry the flags that matter. `i18next-cli` is on the PATH of the image your terminal runs in, not in the app's `node_modules`; call it directly if you need it, never via `npx` (npx cannot see a tool it did not install, so it goes to the network and the sandbox kills that at its time limit).

Copilot (UnifyApps AI agent chat)
- The copilot is assembled from parts, never imported whole: `CopilotProvider` (the runtime), `CopilotChat` (the conversation), `CopilotHistory` (past conversations), `CopilotNewChatButton`, plus the `useCopilotActions()` and `useCopilotStatus()` hooks — all from `@unifyapps/app-builder-sdk/copilot`. `src/components/copilot.tsx` is the app's own composition; edit it freely (layout, chrome, which parts appear). Do NOT import the SDK's prebuilt `<Copilot />` — it is compiled into the bundle and cannot be restyled or rearranged.
- Everything copilot-related must render inside `<CopilotProvider>`; the parts and hooks reach the chat by id through the store it creates and throw outside it. One `<CopilotChat>` per provider — for two copilots on a screen, use two providers with different `instanceId`.
- History and "New chat" are composition, not configuration. There is no `history` prop: place `<CopilotHistory />` and `<CopilotNewChatButton />` (or call `newChat()` from `useCopilotActions`) wherever the layout wants them. Selecting a conversation switches the chat on its own — wire no callbacks.
- Drive your own chrome with the hooks: `useCopilotStatus()` gives `isGenerating` / `chatId` (swap send for stop mid-stream), `useCopilotActions()` gives `sendMessage`, `stopResponse`, `newChat`, `goToChat`. The actions no-op until `<CopilotChat>` has mounted.
- Light/dark: pass `colorScheme` (`'light'` | `'dark'` | `'system'`) to `CopilotProvider` — it drives the design-system tokens and the Joy theme together, scoped to the copilot's own root. The copilot does not read the app's theme by itself, so a dark app that omits this renders a light copilot; bind it to the app's theme state or pass `'system'`.
- Give the chat a bounded height and keep a `min-h-0` chain down to `CopilotHistory`, or the list grows and the page scrolls instead of the list. Import `@unifyapps/app-builder-sdk/copilot.css` once, where the copilot is composed.
- `src/components/copilot.tsx` ships unreferenced — no route imports it, so an app that never asks for a copilot bundles none of it. When the app does need one, add the route yourself and import the component **lazily** (`lazy()` + `Suspense`): it pulls the no-code runtime and every renderable block, ~2.3 MB gzipped, and a static import drags all of that into the entry chunk for every page.

Artifacts (UnifyApps generated files)
- An "artifact" is a file the agent generated in a chat — a deck (PPTX), a doc (DOCX), a PDF, a sheet — saved as an `e_artifact_detail` record. `<Artifact artifactId="e_…" />` from `@unifyapps/app-builder-sdk/artifact` renders it exactly as the copilot canvas does (PPTX/DOCX arrive pre-converted to a PDF preview, original behind a download). It is the SAME viewer the low-code "Artifacts" block uses, not a re-implementation — do NOT try to import the block or `@unifyapps/blocks`; that needs the no-code runtime and will not resolve here.
- `src/components/artifacts.tsx` is the app's own composition (an `Artifacts` wrapper with an empty state); edit it freely. The usual layout is the guided-workspace shape — chat on one side, `<Artifacts>` on the other: the chat surfaces an artifact id, hold it in state and pass it as `artifactId`. Empty/undefined renders the empty state, so bind it straight to "the selected artifact".
- Import the component **lazily** (`lazy()` + `Suspense`) for the same reason as the copilot: it pulls the no-code runtime and the block viewers, the same weight the copilot entry has, and a static import drags it into every page's entry chunk. Load `@unifyapps/app-builder-sdk/copilot.css` once where you compose it — the viewer's styles ride the copilot stylesheet, there is no separate artifact css.
- Resolving the id goes through the platform's `FETCH_ENTITY_BY_ID` automation, so an app user with no entity-type grant still sees the file. That automation must be REGISTERED on the environment. Where it is not, the read falls back to the entity API and a grant-less viewer gets the "unavailable" state instead of the file — if artifacts render for a maker but not for an app user, this is why, and it is an environment/platform fix, not an app one.

Clean Code
- Prefer guard clauses and early returns over nested conditionals.
- Every data-driven view handles loading → error → empty → data (use `Skeleton`; design real empty states, never a blank div).
- Keep components small and single-purpose: hooks own data, presentational children receive props. Split any component mixing fetching, layout, and interaction logic.
- No magic numbers or strings — hoist named constants (UPPER_SNAKE) for limits, keys, durations, statuses.
- Don't drill props past ~2 levels; restructure with composition (children/slots) or context.
- Extract repeated logic into a custom `useXxx` hook and repeated markup into a component — but only on the ~3rd repetition; a wrong abstraction costs more than duplication.
- Name for intent: booleans `isX`/`hasX`/`canX`, handlers `handleX`, callback props `onX`.
- Accessibility: semantic elements (`button`, `nav`, `label` — never a clickable `div`), label every input, `alt` on every image, visible keyboard focus.
- Delete dead code, commented-out blocks, and debug logs as you go.
